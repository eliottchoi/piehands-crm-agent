# 3.1.2. 인증 및 권한 정책 (Authentication & Authorization)

이 문서는 시스템의 인증(누구인가?) 및 권한(무엇을 할 수 있는가?) 정책을 정의합니다.

## 1. 인증 (Authentication)

- **인증 방식:** 모든 팀 멤버 인증은 **Firebase Authentication**을 통해 이루어집니다. 클라이언트(웹 UI)는 Firebase SDK를 사용하여 로그인하고 ID 토큰(ID Token)을 발급받습니다.
- **API 인증:** 백엔드 API 서버(Cloud Run)에 대한 모든 요청은 `Authorization` 헤더에 `Bearer <ID_TOKEN>` 형식으로 ID 토큰을 포함해야 합니다.
- **서버 측 검증:** API 서버는 수신된 모든 ID 토큰에 대해 Firebase Admin SDK를 사용하여 유효성을 검증합니다. 검증 실패 시 `401 Unauthorized` 에러를 반환합니다. 검증이 성공하면, 서버는 요청을 보낸 팀 멤버의 `UID`와 `이메일`을 신뢰할 수 있게 됩니다.

## 2. 권한 (Authorization)

### 2.1. 권한 모델: 역할 기반 접근 제어 (RBAC)

/* --- Backend Note ---
**결정 배경:** 우리는 "단순하게 시작하되, 확장은 용이하게"라는 원칙을 따릅니다. 따라서 현재 v1에서는 세 가지 고정된 역할(Role)을 사용하는 단순한 모델을 채택하여 개발 속도와 관리 용이성을 확보합니다. 하지만 미래에 더 세분화된 권한 제어가 필요할 것을 대비하여, 데이터 모델에는 `permissions` 배열 필드를 미리 설계해 둡니다.
*/

- **현재 정책 (v1):** 권한 검사는 전적으로 Firestore의 `/workspaces/{wsId}/members/{uid}` 문서에 저장된 `role` 필드 값을 기반으로 수행됩니다.
- **미래 계획 (v2):** 더 복잡한 요구사항이 생기면, API 서버의 권한 검사 로직을 `permissions` 배열을 확인하도록 수정할 것입니다. 이를 통해 데이터 구조 변경 없이 유연한 확장이 가능합니다.

### 2.2. 역할 정의 (Role Definitions)

| 역할 (Role) | 설명 | 수행 가능한 작업 (API 기준) |
| :--- | :--- | :--- |
| **`viewer`** | 워크스페이스의 모든 정보를 조회할 수만 있는 읽기 전용 역할입니다. | `GET` 요청만 허용됩니다. (예: 캠페인 목록/상세 조회) |
| **`editor`** | 조회 권한을 포함하여, 캠페인, 템플릿, 유저 등 핵심 리소스를 생성하고 수정할 수 있는 역할입니다. | `GET`, `POST`, `PATCH`, `PUT` 요청이 허용됩니다. 단, 민감한 작업(삭제, 팀원 관리 등)은 제외됩니다. |
| **`admin`** | 모든 권한을 가진 관리자 역할입니다. 워크스페이스 설정, 팀원 초대/삭제 등 모든 작업을 수행할 수 있습니다. | 모든 API 요청(`GET`, `POST`, `PATCH`, `PUT`, `DELETE`)이 허용됩니다. |
