# 3.2.2. 캔버스 노드 상세 명세

이 문서는 각 캔버스 노드의 구체적인 동작 방식, 상태 변화, 설정 가능한 모든 파라미터, 그리고 예외 케이스를 정의합니다. 백엔드 개발자는 이 명세를 기준으로 노드의 실행 로직을 구현해야 합니다.

---

## 1. 흐름 제어 (Flow Control)

### 1.1. 조건 분기 (Conditional Split)

- **역할:** 유저의 속성 또는 이벤트 발생 여부에 따라 여정의 경로를 두 개(Yes/No)로 나눕니다.
- **실행 모드:** 이 노드는 '최대 대기'와 '즉시 평가' 두 가지 모드로 동작할 수 있습니다.

#### 1.1.1. 실행 모드: 최대 대기 (Wait for match)

- **개념:** 노드에 진입한 유저는 설정된 '최대 대기 시간' 동안 조건 충족을 기다리는 `WAITING` 상태가 됩니다.
- **상세 동작:**
  1. 유저가 노드에 진입하면, 시스템은 해당 유저의 `enrollment` 상태를 `WAITING_FOR_CONDITION`으로 변경하고, 타임아웃(Timeout) 작업을 Cloud Tasks에 예약합니다.
  2. 대기 시간 내에 유저가 조건을 만족시키는 이벤트(예: 이메일 오픈)를 발생시키면, 예약된 타임아웃 작업은 취소되고 유저는 즉시 `Yes` 경로로 이동합니다.
  3. 최대 대기 시간이 지나도 조건을 만족시키지 못하면(Timeout), 예약된 작업이 실행되어 유저는 `No` 경로로 이동합니다.
- **설정 파라미터:**
  - `conditionGroup`: 평가할 조건들의 그룹 (AND/OR 논리 포함)
  - `timeoutSeconds`: 최대 대기 시간 (초 단위)

#### 1.1.2. 실행 모드: 즉시 평가 (Evaluate immediately)

- **개념:** 노드에 진입하는 즉시 유저의 현재 속성을 기준으로 조건을 평가하고, `Yes` 또는 `No` 경로로 즉시 이동시킵니다. 대기 시간은 없습니다.
- **상세 동작:**
  1. 유저가 노드에 진입하면, 시스템은 즉시 해당 유저의 Firestore 문서를 조회하여 `conditionGroup`의 조건을 평가합니다.
  2. 평가 결과에 따라 `Yes` 또는 `No` 경로로 즉시 이동합니다.
- **설정 파라미터:**
  - `conditionGroup`: 평가할 조건들의 그룹 (AND/OR 논리 포함)

#### 1.1.3. 조건 빌더 (Condition Builder)

- **요구사항:** 팀 멤버는 UI를 통해 여러 조건을 `AND` 또는 `OR` 논리로 조합하여 복잡한 세그먼트를 정의할 수 있어야 합니다.
- **데이터 구조 예시 (`conditionGroup`):**
  ```json
  {
    "logicalOperator": "AND",
    "conditions": [
      { "property": "level", "operator": "eq", "value": "VIP" },
      { "property": "login_count", "operator": "gt", "value": 30 }
    ]
  }
  ```

#### 1.1.4. 예외 케이스: 캠페인 비활성화
- **정책:** `최대 대기` 모드에서 대기 중인 유저가 있더라도, 캠페인이 `INACTIVE` 상태로 변경되면 해당 유저의 대기는 즉시 중단되고 **여정이 그 자리에서 종료됩니다.** `No` 경로로 이동하지 않습니다.

---
### 1.2. 시간 대기 (Wait)

- **역할:** 다음 단계로 넘어가기 전, 설정된 시간만큼 유저의 여정을 일시 중지시킵니다.
- **상세 동작:**
  1. 유저가 노드에 진입하면, 시스템은 설정된 대기 시간 후 다음 노드를 실행하도록 Cloud Tasks에 작업을 예약합니다.
  2. 해당 유저의 `enrollment` 상태는 `WAITING_FOR_TIME`으로 변경됩니다.
  3. 예약된 시간이 되면, Cloud Tasks가 작업을 실행하여 유저를 다음 노드로 이동시킵니다.
- **설정 파라미터:**
  - `waitDuration`: 대기할 시간 (예: `{"value": 2, "unit": "hours"}`)
  - `waitUntil`: 특정 날짜/시간까지 대기 (예: `"2025-12-25T09:00:00+09:00"`)
  - `waitMode`: `duration` 또는 `timestamp` 중 어떤 것을 사용할지 결정
- **예외 케이스: 캠페인 비활성화**
  - **정책:** 대기 중인 유저가 있더라도 캠페인이 `INACTIVE` 상태로 변경되면, 예약되었던 모든 Cloud Tasks 작업은 **취소되고 여정이 그 자리에서 종료됩니다.**

### 1.3. A/B/n 테스트 (Split)

- **역할:** 유저를 무작위로 여러 경로(Branch)로 분산시켜 어떤 여정이 더 효과적인지 실험합니다.
- **상세 동작:**
  1. 유저가 노드에 진입하면, 시스템은 설정된 비율에 따라 무작위로 경로 중 하나를 선택합니다.
  2. 선택된 경로로 유저를 즉시 이동시킵니다.
  3. 어떤 유저가 어떤 경로로 분기되었는지는 `campaign_enrollments` 문서에 기록되어야 성과 측정이 가능합니다.
- **설정 파라미터:**
  - `branches`: 각 경로의 이름과 트래픽 비율을 담은 배열. 전체 합은 반드시 100%여야 합니다.
    ```json
    [
      { "name": "Branch A", "percentage": 50 },
      { "name": "Branch B", "percentage": 50 }
    ]
    ```
- **유효성 검사:**
  - 팀 멤버가 노드 설정을 저장할 때, 모든 `branches`의 `percentage` 합이 100이 아닌 경우 오류 메시지를 표시하고 저장을 막아야 합니다.

## 2. 액션 (Actions)

### 2.1. 이메일 발송 (Send Email)
- **역할:** 특정 템플릿을 사용하여 유저에게 이메일을 보냅니다.
- **상세 동작:**
  1. 유저가 노드에 진입하면, 시스템은 해당 유저의 속성과 템플릿을 조합하여 최종 이메일 콘텐츠를 생성합니다.
  2. 생성된 콘텐츠를 SendGrid API로 전송하여 발송을 요청합니다.
  3. 발송 요청 성공/실패 여부를 `campaign_enrollments` 문서에 기록합니다.
- **설정 파라미터:** (캠페인 편집기 문서의 테이블 참조)
- **예외 케이스:**
  - **수신 거부 유저:** 발송 시점에 유저가 수신 거부 목록(`Do Not Contact`)에 있다면, 실제 발송은 일어나지 않고 `SKIPPED` (사유: `unsubscribed`) 상태로 기록됩니다.
  - **SendGrid API 에러:** API 호출이 실패하면, 설정된 재시도(Retry) 정책에 따라 몇 차례 재시도 후, 최종 실패 시 `FAILED` 상태로 기록됩니다.

### 2.2. 유저 속성 업데이트 (Update Property)
- **역할:** 유저의 속성 값을 변경합니다.
- **상세 동작:**
  1. 유저가 노드에 진입하면, Firestore의 해당 유저 문서에 있는 속성(Property) 필드를 업데이트합니다.
  2. 이 변경 사항은 해당 유저의 활동 피드에도 기록되어야 합니다.
- **설정 파라미터:** (캠페인 편집기 문서의 테이블 참조)

## 3. 시작 조건 (Triggers)

### 3.1. 이벤트 기반 (Event Trigger)
- **역할:** 특정 이벤트가 발생한 유저의 여정을 시작시킵니다.
- **상세 동작:**
  1. Events API를 통해 새로운 이벤트가 수집됩니다.
  2. 시스템은 해당 이벤트를 트리거로 사용하는 모든 `ACTIVE` 캠페인을 찾습니다.
  3. 캠페인의 `이벤트 속성 필터` 조건과 이벤트의 속성을 비교합니다.
  4. 모든 조건이 일치하면, 해당 유저에 대한 `campaign_enrollments` 문서를 생성하여 캔버스 여정을 시작시킵니다.
- **설정 파라미터:** (캠페인 편집기 문서의 테이블 참조)
- **중요 정책: 재진입(Re-entry) 방지**
  - **기본 정책:** 한 명의 유저는 하나의 캠페인에 **단 한 번만** 참여할 수 있습니다. 이미 `campaign_enrollments` 문서가 존재한다면, 동일한 트리거가 다시 발생해도 여정을 새로 시작하지 않습니다.
  - **(미래 기능):** 향후 캠페인 설정에서 재진입 허용 옵션(예: "구매 완료" 이벤트마다 여정 새로 시작)을 추가할 수 있습니다.
